# Work 元数据与 SQLite 稳定性设计

## 目标

在不改变真实漫画文件、不触碰正式 `6680` 服务的前提下，稳定 `17680` 测试版，并把漫画元数据管理统一到 `Work`（整部漫画）层级：

- 所有 Work 读取接口只读数据库，不再在 GET 请求中迁移、建档或同步关系。
- 扫描只负责发现和更新内容，不再自动触发在线元数据刮削。
- 漫画元数据页面每部漫画只显示一个 Work；小说保持单本 Comic 流程。
- 书库管理增加“立即刮削”，按当前书库的 Work 顺序处理整部元数据。
- 数据库繁忙与真正不存在必须在 API 和界面上明确区分。

## 数据边界

```text
Work（用户看到的一整部漫画）
  └─ Unit（卷、话、番外或整本）
       └─ Comic（物理文件/文件夹及页面资源）
```

漫画的标题、作者、简介、封面、标签、分类和刮削状态写入 `LogicalWork`。Unit/Comic 只保留阅读、文件解析、页码和物理资源职责。小说继续使用现有 Comic 元数据。

## SQLite 并发

SQLite 使用 WAL 和多连接读取池。核心稳定性规则：

1. GET `/api/works`、`/api/works/:id`、`/api/works/:id/units` 不执行任何写入。
2. `ComicSeries -> LogicalWork` 迁移只在显式迁移阶段执行。
3. Work 的检测结果只在扫描成功后持久化。
4. Work 元数据写入使用统一串行写锁，并对 `SQLITE_BUSY` 做有限指数退避。
5. 前台读取不与长时间后台任务共享唯一数据库连接。

## 扫描与刮削

扫描完成后：

1. 更新 Comic 物理记录。
2. 重建受影响书库的 Work 布局并持久化。
3. 清理 Work 缓存。
4. 结束。

扫描不会调用在线刮削。手动刮削仍要求站点刮削功能已启用。

“立即刮削”调用书库级 Work 批处理接口。默认只处理缺少可靠元数据或封面的 Work；同一 Work 只搜索和应用一次，不遍历每个 Unit/Comic。接口返回任务总数、成功、失败、跳过和当前进度。

## 元数据页面

- `contentType=comic`：从 Work API 获取并分页，每部漫画一项。
- `contentType=novel`：继续使用现有 Comic 元数据 API。
- `contentType=all`：分别获取漫画 Work 和小说 Comic，在前端统一展示，不把漫画 Unit 展开。
- 单项搜索、应用、批处理均根据实体类型调用对应 API。

## 错误处理

- 404：作品确实不存在或无权访问。
- SQLite 繁忙：返回 `503` 和稳定错误码 `database_busy`。
- 其他内部错误：返回 `500` 和 `load_failed`。
- 前端只在 404 显示“漫画不存在”；503 自动进行有限重试并显示“服务繁忙”。

## 验证范围

- 回归测试证明所有 Work GET 路径不写数据库。
- 并发读写测试证明读取不会因后台 Work 写入持续失败。
- 扫描测试证明不会自动刮削，但会持久化 Work 布局。
- 元数据接口测试证明漫画按 Work、小说按 Comic。
- 书库级手动刮削测试证明一部漫画只入队一次。
- 前端类型检查、测试和生产构建。
- 仅在 `17680` 容器进行连续 API 与真实页面验证。
